# ARG-003 · Таймауты внутренних REST-вызовов на 231 хосте, MongoDB (mongos) — подозреваемая причина

**Исполнитель:** DBA · **Severity:** SEV-1 · **Начало:** 25.08 02:40 UTC · **Обнаружено:** 25.08 03:00 (через 30 мин) · **Закрыт:** 25.08 20:20

## Что происходит

С 25.08 02:30 резко выросли таймауты внутренних REST-вызовов: «Rest error: Operation timed out…» дошли до 259 674 за 10 минут при обычных 110,5. Это и есть основной поток 5xx: 395 857 строк с 5xx, затронута 233 из 278 хостов. С 02:40 появились новые сигнатуры MongoDB-драйвера (monitor timeout, Socket timed out, очистка пула mongos.local-services.svc.cluster.local). Они почти целиком приходят с kube0129.infra.internal. RPS и CPU не изменились, поэтому версия о нагрузке не подтверждается. Наиболее вероятно, что недоступен mongos/MongoDB, но рост REST-таймаутов на несколько минут опережает первые ошибки драйвера, так что причинность ещё нужно подтвердить.

- Нагрузка ровная: RPS 66 866 → 67 470, CPU 20,5 % → 21,9 %; пиковая доля ошибок 0,718 %

## Возможные причины

1. **Деградация или потеря связности с mongos / репликасетом MongoDB (mongos.local-services.svc.cluster.local). Внутренние сервисы, которые на нём работают (entity list, Privileges API), висят до таймаута, и он каскадом расходится по всем подам** — Новые сигнатуры драйвера с указанием mongos: monitor timeout, Socket timed out, очистка пула. Появились в 02:40–02:52 и до этого не встречались. CPU и RPS ровные, то есть REST-таймауты — симптом зависимости, а не перегрузки приложения _(уверенность: средняя)_
2. **Сетевая проблема или проблема DNS в кластере (Service mongos / внутренние сервисы), и Mongo-ошибки — только один из её симптомов** — Ошибки драйвера видны только с двух хостов (kube0129, kube0127), а REST-таймауты есть на 231 хосте и начали расти уже в окне 02:30–02:40, до первой Mongo-ошибки в 02:40:25 _(уверенность: низкая)_
3. **Отказ самого бэкенд-сервиса, который отдаёт entity list и privileges (зависание, исчерпание воркеров), без причины на уровне инфраструктуры** — «Failed get entity list» начал расти первым, с 02:30. Прямых признаков отказа сервиса в логах нет _(уверенность: низкая)_
