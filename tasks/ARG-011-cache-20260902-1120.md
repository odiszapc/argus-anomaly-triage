# ARG-011 · Сбой Valkey (LOADING, MOVED) и таймауты внутреннего REST API на 238 хостах: 5xx, CPU 95 %

**Исполнитель:** DBA · **Severity:** SEV-1 · **Начало:** 02.09 11:20 UTC · **Обнаружено:** 02.09 11:30 (через 20 мин) · **Закрыт:** 02.09 23:30

## Что происходит

В 11:28 на всех хостах одновременно появились таймауты внутреннего REST API (106,4 тыс. строк за минуту), а через минуту начались ошибки Redis. Новые всплески пришли в 11:36 (Rest error и MOVED на 168 строках) и в 11:39: тогда впервые за 14 дней появилась ошибка «LOADING Valkey is loading the dataset in memory» (215,2 тыс. строк, 36 хостов). Похоже на рестарт или failover узлов Valkey со сменой карты слотов. Из-за промахов кэша растёт нагрузка на REST/GRPC-бэкенды, CPU держится на 95 %. Затронуто не меньше 114,8 тыс. клиентов, 5xx — 137,1 тыс. строк.

## Симптомы

- 11:28–11:29: «Rest error: Operation timed out…» — 106 425 и 30 276 строк в минуту на 238 хостах. Волны повторились в 11:36 (195 776) и 11:39 (118 412)
- Ошибки «Unexpected Redis exception» и «Redis failure» с 11:28: 934 строки в 11:29. В 11:36 появились MOVED (168 строк, 32 хоста)
- 11:39: впервые в истории «LOADING Valkey is loading the dataset in memory», 215 249 строк на 35–36 хостах (kube0127, kube0401, kube0129 и др.)
- В корзине 11:40 одновременно «Server error: {…}» (205,8 тыс.), «GRPC invalid response code» (2 068 при норме 4) и «Privileges API not available» (295)
- CPU приложений: 95,2 % против 17,6 % вчера. RPS упал до 61,7 тыс. в корзине 11:30, затем вырос до 136,6 тыс. в 11:40 при норме 67,9 тыс. (вероятно, ретраи)
- Хиты по странам просели равномерно (IN 0,57; US 0,63; DE 0,57; FR 0,63), привязки к одной стране нет

## Возможные причины

1. **Рестарт или failover узлов Valkey: узлы загружают датасет (LOADING), карта слотов меняется (MOVED), клиенты получают ошибки и таймауты, и лавина промахов уходит в бэкенды** — LOADING появился впервые (never_seen_before) в 11:39 на 36 хостах. MOVED с 11:36. Redis exception/failure начались в 11:28–11:29, в ту же минуту, что и REST-таймауты. Rules engine относит компонент к кэшу _(уверенность: высокая)_
2. **Деградация внутреннего REST API (entity list, Privileges) как самостоятельная причина. Ошибки Redis в этом случае вторичны** — В 11:28 на 238 хостах 106 425 REST-таймаутов и всего 7 ошибок Redis на 3 хостах. Похожий инцидент ARG-008 (31.08, Backend Lead) и открытый ARG-011 с 11:28 _(уверенность: средняя)_
3. **Перегрузка CPU приложений из-за ретраев или промахов кэша. Это скорее усилитель, чем первопричина** — CPU вырос с 20,4 % до 95,2 % в корзине 11:30. RPS в 11:40 — 136,6 тыс. против нормы 67,9 тыс., а хиты по странам при этом падают _(уверенность: низкая)_

## Почему DBA

Согласен с rules engine: впервые появившиеся LOADING и MOVED прямо указывают на рестарт или решардинг узлов Valkey, а ошибки Redis начались в ту же минуту, что и REST-таймауты. Backend Lead (ARG-011) стоит держать в курсе: если кэш окажется здоров, первопричиной остаётся REST API.

Голоса: правила — DBA · аналитик — DBA · арбитр — DBA

## Что проверить в первую очередь

- [ ] Проверить состояние кластера Valkey: CLUSTER INFO / CLUSTER NODES, INFO persistence (loading:1), uptime узлов. Найти, какой узел рестартовал или сделал failover около 11:28 и 11:36–11:39
- [ ] Посмотреть события Kubernetes по подам Valkey (OOMKilled, eviction, рестарт пода, сработавшая liveness-проба) и использование памяти на узлах
- [ ] Убедиться, что клиенты на kube0127/kube0401/kube0129 обновили карту слотов после MOVED. При необходимости перезапустить проблемные поды приложения
- [ ] Параллельно проверить latency и health внутреннего REST API (entity list, Privileges) и GRPC: сравнить, зависят ли они от того же кэша
- [ ] Если LOADING затягивается, ограничить ретраи или включить деградацию без кэша, чтобы снять нагрузку CPU 95 %
