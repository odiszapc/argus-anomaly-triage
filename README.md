# Argus — аномалии в метриках и логах → задачи, Slack и post-mortem

Argus следит за метриками и логом ошибок веб-приложения. Он находит аномалии без заглядывания в будущее и на каждый инцидент создаёт три вещи:

- задачу на триаж с симптомами, гипотезами о причинах, оценкой затронутых пользователей и исполнителем;
- сообщение в `#app-alerts`;
- черновик post-mortem.

Аномалии находит статистика. Текст задачи пишет LLM-агент с read-only SQL, после чего код проверяет каждое число в этом тексте. Исполнителя выбирают голосованием правила, LLM-аналитик и локальная модель другого семейства. Если голоса разошлись, решает человек.

**С чего начать:** [`report.html`](report.html) (обзор прогона), [`tasks/`](tasks/), [`postmortems/`](postmortems/), [`slack-log.json`](slack-log.json), [`evals/results.md`](evals/results.md).

## Как устроено

```
файлы/Prometheus/Loki ──► ingest (DuckDB) ──► детекторы ──► IncidentBook ──► дедупликация ──┬─► LLM-аналитик (Claude, SQL-инструмент)
                                 │            причинные:     корреляция,      повтор → тред  │      └► проверка чисел кодом
                                 │            без look-ahead severity, жизнь                 ├─► арбитр (Qwen3, «слепые» факты) → голосование
                                 └─ views с фильтром по now                                  └─► tasks/*.md · slack-log.json · postmortems/*.md
                                                                                                  прогноз повтора → #app-alert-predictions
```

- **Детекторы** ([`src/argus/detect/`](src/argus/detect/)) сравнивают значение с медианой того же времени суток за прошлые дни и оценивают шум по MAD.
  - RPS сверяется с независимыми сигналами (CPU, счётчик по странам). Неподтверждённые скачки считаются артефактом и никого не будят.
  - Страна сравнивается с медианным сдвигом всех стран, поэтому общий рост трафика не попадает к SEO.
  - Бот определяется так: обычно невидимый провайдер внезапно даёт большую долю запросов, и каждый запрос идёт с нового IP.
- **Корреляция** ([`correlate.py`](src/argus/correlate.py)) склеивает симптомы (таймауты, 5xx) с причиной (БД, кэш, DNS, код). Многодневные регрессии держатся по уровню до инцидента, а не по адаптивному бейзлайну. Задача открывается, если сбой устойчивый, крупный или повторяющийся; короткие вспышки остаются «блипами».
- **Маршрутизация** задаётся в [`config/routing.yaml`](config/routing.yaml): компонент → роль, причина или симптом, стартовые гипотезы. Её правят в конфиге, а не в коде.
- **LLM-слой** ([`src/argus/llm/`](src/argus/llm/)) состоит из трёх частей.
  - Аналитик: агент Claude Agent SDK с одним инструментом, read-only SQL по данным «на момент алерта». Отвечает по JSON-схеме.
  - [`verify.py`](src/argus/llm/verify.py) сверяет каждое число в тексте с фактами и с результатами запросов агента.
  - Арбитр видит только факты, без мнения правил и аналитика.
  - Если правила опираются на ни разу не виденную сигнатуру-причину, модели не могут молча их переголосовать.
- **Дедупликация** ([`dedup.py`](src/argus/dedup.py)): перед созданием задачи ищется уже существующая задача по той же проблеме. Совпадение определяется по сигнатурам и эмбеддингам `qwen3-embedding`. Новый тип сбоя всегда получает отдельную задачу.
- **Прогноз** ([`predict.py`](src/argus/predict.py)): после сбоя хранилища, начавшегося под нагрузкой, система предупреждает о риске повтора к моменту, когда трафик снова дойдёт до того же уровня. Время берётся из прогноза RPS по тем же часам прошлых дней.

Подробности: [`docs/architecture.md`](docs/architecture.md), анализ данных и выбор методов: [`docs/analysis.md`](docs/analysis.md), решения по ходу работы: [`docs/decisions.md`](docs/decisions.md).

### Где ИИ, а где классика

| Часть | Чем | Почему |
|---|---|---|
| Поиск аномалий, склейка, влияние, severity | статистика + SQL | детерминированно, тестируемо, 14 дней за 30 с, без галлюцинаций |
| Гипотезы, проверка их запросами, текст задачи, выбор исполнителя в спорных случаях | Claude (агент) | нужно читать сообщения об ошибках и связывать сигналы, как дежурный инженер |
| Числа в тексте | код | модель не может «округлить» факт: неподтверждённое число попадает в задачу с пометкой |
| Второе мнение | Qwen3 14B локально | модель другого семейства не повторяет ошибки первой; данные не уходят наружу |
| Повторы | сигнатуры + эмбеддинги | дёшево и объяснимо: модель не нужна, чтобы узнать «то же самое ещё раз» |

## Быстрый старт

Нужны Python 3.12 и [uv](https://docs.astral.sh/uv/). Для LLM-режима нужен `ANTHROPIC_API_KEY` или залогиненный Claude Code, а также Ollama с `qwen3:14b` и `qwen3-embedding:0.6b`.

```bash
make setup                        # зависимости
make ingest DATA=../data          # 16 ГБ logs.json + CSV → var/argus.duckdb, ~30 с
make replay-offline eval          # 14 дней только правилами (~30 с) и оценка по эталону
make replay eval report           # с LLM-аналитиком и арбитром: tasks/, postmortems/, slack-log.json, report.html
```

Режимы: `argus replay` прогоняет историю как живую, `argus run` делает один проход от сохранённого курсора (для cron и Kubernetes CronJob), `argus watch --interval 300` работает резидентно. Повторный запуск не дублирует задачи и сообщения. `ARGUS_LLM=claude|local|off` выбирает, где работает анализ: `local` держит всё на Ollama, `off` оставляет только правила. В облако уходят только факты по инциденту (до 10 КБ) и результаты SQL (до 50 строк).

Развёртывание: [`Dockerfile`](Dockerfile), [`docker-compose.yml`](docker-compose.yml) (Argus + Ollama), [`deploy/k8s/cronjob.yaml`](deploy/k8s/cronjob.yaml), CI — [`.github/workflows/ci.yml`](.github/workflows/ci.yml).

## Поддержка агентами

- [`AGENTS.md`](AGENTS.md) (он же `CLAUDE.md`) содержит карту кода, инварианты (их держат тесты) и порядок изменений.
- [`.mcp.json`](.mcp.json) подключает `argus mcp`: SQL, схему, список задач и чтение задачи для Claude Code и других агентов.
- Skills в [`.claude/skills/`](.claude/skills/): разбор инцидента, безопасная настройка детекции с `make eval`, подключение Prometheus, Loki или ClickHouse.
- `make eval` после любой правки порогов показывает recall, точность назначения, время до оповещения и задачи без метки.
- 111 тестов на синтетических данных, без сети и моделей.

## Как ИИ использовался при разработке

- Анализ 16 ГБ данных вёл Claude Code как агент. Он писал SQL к DuckDB, проверял гипотезы и отбрасывал ложные, например «скачки RPS — это трафик».
- Он же построил визуальный отчёт с находками и составил план реализации.
- Реализация шла по TDD с журналом проектных решений ([`docs/decisions.md`](docs/decisions.md)).
- Субагенты выполнили линт, страницу отчёта, документацию и финальное ревью.
- Пороги откалиброваны на прогонах replay: каждая правка начиналась с теста, воспроизводящего ошибку на реальных данных.

## Ограничения

- Эталон собран вручную, данных всего две недели: недельной сезонности нет, первые два дня работает холодный старт.
- В логе только ошибки, поэтому «затронутые пользователи» — нижняя граница, а латентность видна только по топу эндпоинтов раз в 30 минут.
- Влияние многодневной регрессии (ARG-006) накапливается за все её дни.
- Прогноз умеет только сценарий «повтор сбоя хранилища при росте нагрузки».

Что улучшить в самом процессе (метка выкладок, исправление метрики RPS, обратная связь из Slack в эталон): [`docs/process-improvements.md`](docs/process-improvements.md).
